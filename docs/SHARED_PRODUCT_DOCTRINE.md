# Shared Product Doctrine

This document is a reusable portfolio doctrine template for operator-facing
systems software.

Use it to keep product framing aligned across repos without forcing the products
to feel identical.

## Core Doctrine

Build operator-first systems software that makes infrastructure, access, and
network operations safer, clearer, and faster.

## Shared Principles

- operator-first workflow over ornamental UI
- high signal, low noise
- clear trust boundaries
- practical workflows first, automation second
- local authority over hidden background behavior
- release discipline over feature sprawl

## Shared Language

Prefer phrasing like:

- operator-first
- safer, clearer, faster
- trust boundary
- practical workflow
- high signal
- reduced context switching
- explicit approval

Avoid flattening every product into the same category. The doctrine should
align values, not erase product identity.

## Product-Specific Specialization

Each product should answer:

1. what operator job it owns
2. what workflows it unifies
3. what it is intentionally not
4. how it relates to the rest of the portfolio

Example portfolio split:

- `Citadel`: identity operations and access governance
- `NetRadR`: network visibility and intelligence
- `Zenith`: operator terminal and execution
- `Feox`: kernel-and-runtime foundation

## Recommended Repo-Level Sections

Each product README and positioning doc should try to include:

- who it is for
- what problem it solves
- product principles
- current capabilities
- current maturity
- architecture at a glance
- portfolio role
- what it is not

## Notes

- Share doctrine and release discipline.
- Do not force shared UI metaphors.
- Do not force the same visual identity.
- Let each product keep its own interaction model and mood.
